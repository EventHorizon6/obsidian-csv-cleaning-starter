How to find CSV import problems before they break your upload

A product, customer or order export can look fine in a spreadsheet and still fail an import, or worse, import the wrong data. This worked example runs the free Data Rescue Scanner on a small synthetic product export and explains every problem it reports. What each problem means

Row with the wrong number of cells high

Why it matters: Values shift into the wrong columns, usually because of a stray delimiter or quotation mark.

What to do: Check the row for an extra or missing delimiter, or a value containing the delimiter that is not quoted.

Found in the sample:

  • Row 10, (whole row): row has 6 cells where the header has 7; the missing cells were treated as blank

Spreadsheet formula risk high

Why it matters: A cell starting with =, +, - or @ can run as a formula when the file is opened in a spreadsheet (CSV injection).

What to do: Treat the file with care. Remove the leading character, or prefix the cell with an apostrophe before opening the file in a spreadsheet.

Found in the sample:

  • Row 7, notes: starts with a character a spreadsheet would run as a formula (=SUM(A1:A9))
  • Row 9, notes: starts with a character a spreadsheet would run as a formula (@restock)

Same identifier, different details high

Why it matters: Two rows share an identifier but disagree on other fields, so an import may keep the wrong one or overwrite the right one.

What to do: Decide which row is correct for each identifier before importing.

Found in the sample:

  • Row 3, product_id: same product_id as row 6 but different values in: price (P-1002)
  • Row 6, product_id: same product_id as row 3 but different values in: price (P-1002)

Date that cannot be read high

Why it matters: The value looks like a date but is not a real calendar date (for example month 13), so it may be rejected or misread.

What to do: Correct the date in the source system and re-export.

Found in the sample:

  • Row 8, launch_date: looks like a date but is not a valid day-first calendar date (31/13/2025)

Exact duplicate row medium

Why it matters: Importing both copies can double-count stock, orders or contacts.

What to do: Remove the extra copy if it is not intentional.

Found in the sample:

  • Row 11, (whole row): identical to row 10

Inconsistent value in a numeric column medium

Why it matters: Most values in the column are numbers, but this one is text or uses a different format, so an import may reject it or read it as zero.

What to do: Make every value in the column a plain number, or leave the cell empty.

Found in the sample:

  • Row 2, price: reads as 24, but uses currency, percent or thousands marks in a column that also holds non-numeric values ($24.00)
  • Row 4, price: not a number, but other values in this column are numbers (N/A)
  • Row 9, price: not a number, but other values in this column are numbers (twenty)

Leading zeros at risk medium

Why it matters: Spreadsheets and number conversions drop leading zeros, which breaks barcodes, postcodes, account numbers and SKUs.

What to do: Keep the column as text when opening or importing the file.

Long number that spreadsheets round medium

Why it matters: Spreadsheets keep only 15 significant digits, so longer numbers are silently changed or shown in scientific notation.

What to do: Keep the column as text when opening or importing the file.

Found in the sample:

  • Row 7, barcode: 19 digits; spreadsheets keep only 15 significant digits (1234567890123456789)

Missing value medium

Why it matters: Required fields that are empty are a common reason for rejected or incomplete imports.

What to do: Fill the values that your import requires; leave optional ones empty.

Found in the sample:

  • Row 2, notes: no value in this field

Placeholder instead of an empty value low

Why it matters: Text such as N/A, null or a dash is imported as text, not as an empty value.

What to do: Replace placeholders with empty cells if the target system expects blanks.

Found in the sample:

  • Row 4, price: reads as an empty value (N/A)

Line break inside a cell low

Why it matters: Quoted line breaks are valid CSV, but some import tools and scripts split the row at the line break.

What to do: Check that your import tool accepts multi-line cells, or replace the line break with a space.

Found in the sample:

  • Row 8, notes: the value contains a line break (Ships in two ⏎ parcels)

Extra spaces low

Why it matters: Leading, trailing or doubled spaces make identical values look different, which breaks matching and de-duplication.

What to do: Trim the spaces.

Found in the sample:

  • Row 3, title: extra spaces at the start, end or middle of the value (Ceramic mug )

What a scan cannot tell you

  • Whether a value is true. A price of 19.5 can be valid and still be the wrong price.
  • Which of two conflicting rows is correct. That is a business decision.
  • Whether a particular platform will accept the file. Each import template has its own required columns and rules.
  • Near-duplicates such as "Ceramic Mug" and "ceramic mugs". The scanner reports exact matches only.

Fixing the problems yourself

  1. Make a copy of the export and work on the copy.
  2. Fix the high-priority findings first: wrong cell counts, formula risks, conflicting identifiers and unreadable dates or numbers.
  3. When opening the file in a spreadsheet, import identifier, barcode and postcode columns as text so leading zeros and long numbers survive.
  4. Save as CSV UTF-8 and scan the result again before importing.

From a messy CSV to a checked delivery: an eight-row example

This is synthetic demonstration data, not a customer project. Scanning finds problems; cleanup is a separate step that must be checked against the original.

Before:

After:

In the complete eight-row example: - All eight records remain, in the same order and with the same columns. - Dates with evidence of day-first order become YYYY-MM-DD. Do not guess a date convention from one ambiguous value. - Numeric formatting is standardised where the whole column supports that interpretation. - An exact repeated row stays in the file and is flagged. Records sharing an ID but disagreeing also stay and are flagged; deciding which is correct is not a formatting task. - A missing amount stays empty. The report does not invent a value. - A formula-like value is marked as text in the file intended for spreadsheet opening. The separate machine-import file does not have that safety marker; do not open it as a spreadsheet.
